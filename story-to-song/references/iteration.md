# 迭代协议

## 总原则

- **只改用户指出的，和由此牵连的。** 其余一个字不动，并在回复里明确说"哪些没动"。
- **改前先确认理解对了。** 如果用户的意思有两种可能，先用一句话复述并确认，再改。这次实战里的几次返工，都是因为没确认就改。
- **每改完一轮，立刻覆盖 `歌词定稿.md`，再重跑校验脚本。**

## 用户反馈的常见类型

| 用户说 | 先做什么 |
|---|---|
| "这里不对"（事实） | 回到 `故事笔记.md` 核对；错在场景、渠道还是时间？改正后更新笔记 |
| "太直白/太俗" | 用 `polish.md` 的「直白→动作」：问"他当时手上在做什么"，换成动作；只改被指的句子，说明做法，之后同类问题自己主动查 |
| "太长/唱不动" | 看是哪种原因（一句两意、叙述不是画面、字多），再处理，别笼统砍字 |
| "不像我说的" | 问："那你会怎么说？" 用他的原话做基础 |
| "不够好"（没说哪里） | 不要整篇重写。指出 2–3 个你自己觉得最弱的句子，问是不是这里 |
| "回到上一版" | 从 `旧版/` 恢复，不重写 |
| "两个选一个"（如歌名） | 给出各自的理由和代价，给一个明确推荐，由用户选 |

## 局部修改的顺序

1. 复述要改什么、不动什么。
2. 改。
3. 覆盖定稿，跑脚本。
4. 回复：新句子、为什么这样改、**哪些没动**、脚本结果。

## 连锁影响

改一个地方，要检查有没有牵连：

- 改了某句的韵脚 → 同段其他句是否仍押韵
- 改了钩子句 → 3 次重复是否同步
- 改了歌名 → 词里是否出现了点破
- 改了事实 → 其他段是否还留着旧说法

## 满意的标志

用户说"可以""不错""就这样"，或开始问提示词/曲风，就可以收尾：整理 `创作注解.md`，再进入选平台、出提示词。
