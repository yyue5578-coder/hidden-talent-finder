# 故事成歌

把一个故事写成可以唱的中文歌词，再变成一首能听的歌。面向**零基础**的人，不要求懂乐理、不要求会写词。

`SKILL_DIR` 指本 `SKILL.md` 所在的目录，下文的 `references/`、`knowledge_base/`、`scripts/`、`templates/` 都在它下面。

## 核心原则

1. **入口按场景和感觉，不按曲风。** 小白答不出"要什么曲风"，但答得出"写给谁、想让人听完是什么感觉"。
2. **先词后曲。** 小白只有看到词，才知道这首歌该是什么氛围，所以先写词，再选曲风，最后出歌。
3. **用户当"挑剔的人"，AI 当写的人。** 用户只需判断"这句对不对、像不像我"。小白常说不出哪里不好，由你主动提出诊断问题（见 `references/polish.md`）。
4. **不用术语。** 对用户别说 BPM、泛音、Pre-Chorus，要说"慢一点、安静一点、像在耳边说话"。术语只出现在最后生成的提示词里。
5. **一次最多问 3 个问题。** 先给选项，再让用户补充。
6. **落盘，只认一份定稿。** 每改完一版就写入文件，不要让多个版本并存。

## 何时使用

- 用户要写歌、写歌词，或要改、检查已有歌词。
- 用户要为歌词生成 Suno 或海绵音乐的提示词。

## 产出文件约定

在当前工作目录下建 `我的歌/{歌名或暂定名}/`，里面只放：

| 文件 | 内容 |
|---|---|
| `歌词定稿.md` | **只放歌词**，带英文段落标签，如 `[Verse 1]` `[Chorus]`。不放注解，方便校验脚本和 Suno 直接用 |
| `创作注解.md` | 创作方向、韵脚方案、技法说明、事实与想象对照、配比检查。按 `templates/创作注解.md` 写 |
| `故事笔记.md` | 用户讲的故事、已核实的事实、想象的部分 |
| `提示词-Suno.md` / `提示词-海绵音乐.md` | 选定平台的提示词，两个都要就各存一份 |
| `旧版/` | 被替换的旧版本，文件名带日期 |

每改一轮就覆盖 `歌词定稿.md`，只认这一份。用户说"回到最初那版"，从 `旧版/` 恢复，不要凭印象重写。

## 工作流

### 1. 判断信息够不够

- 用户已经讲了故事和感觉 → 整理成故事笔记，请用户确认，进入第 2 步。
- 信息不足 → 读 `references/questions.md`，一次最多问 3 个问题。
- 用户答不出"发生了什么"，只想给某个人写一首歌 → 走 `questions.md` 里的「没有具体事件的用户」，问碎片，不编事件。

### 2. 核实事实

- 涉及真实人物或真实事件 → **必须联网查证**，按 `references/polish.md` 的「事实核对」和 `references/rules.md` 第七节「真人题材规矩」做。事实分三档（多源一致 / 单一来源 / 互相矛盾），分开记进 `故事笔记.md`。
- 纯个人故事（朋友、家人、自己）→ 只请用户确认关键细节，不联网。

### 3. 定场景，调知识库

当前覆盖六个场景：**怀念/释怀**、**暗恋/心动**、**生日/祝福**、**纪念/求婚**、**道歉/感谢**、**亲情**。

- 读 `knowledge_base/{场景}__profile.md`，取它的情绪弧线、常用意象、钩子手法和常见坑。
- 同目录下如果有该场景的单曲拆解（`{场景}__{歌名}.md`），挑 1–2 首最贴近的参考。
- **先看 profile 顶部的"可信度"。** 可信度为"低"（暗恋/心动、生日/祝福；纪念/求婚的"回望式纪念"子类没有样本；道歉/感谢整体为低）时，要告诉用户"这个场景的参考样本不足"，并以 `references/rules.md` 为主，不要把 profile 当范本。
- 纪念/求婚分三个子类（求婚 / 恋爱纪念 / 结婚纪念），先分清再读 profile 对应的弧线。
- 道歉/感谢分两个子类。**写之前必问**：道歉问"对不起的是哪一件事"，感谢问"TA 做过的哪件小事你还记得"；没问到就不要开写，也不要替用户编。样本普遍只有"对不起/谢谢"三个字，没有事，要借句式，不借配比。
- 亲情分三种关系（子女→父母祖辈 / 父母→孩子 / 手足）。**写之前必问**：TA 在世吗（当面送在世的人，别用悼词口吻）、TA 做过的哪件小事你还记得；不猜性别，不猜爸妈；写孩子不替孩子编话，不写未成年人全名学校。样本普遍是清单、赞歌、说教，借手法，不借概括词。
- 单曲文件开头有"贴合度"，使用前先看，别把不贴场景的歌当范本。
- 场景不在六个之内，或知识库缺失 → 跳过调库，只用 `references/rules.md`。

### 4. 方向确认（开写前必做）

输出一段不超过 80 字的概要，用户确认后再写：

```
创作方向
场景与感觉：
核心画面：（2–3 个具体的东西）
情绪走向：
韵脚方案：主歌 ×× 韵 → 副歌 ×× 韵
钩子构思：
```

用户说"直接写"就跳过确认。

### 5. 写词

读 `references/rules.md`，按它写。要点：

- 先定全曲韵脚，再逐段写。
- 写完整首后，立刻把歌词存进 `歌词定稿.md`，**运行校验脚本**：

```
python3 SKILL_DIR/scripts/check_lyrics.py 歌词定稿.md
```

  把 `SKILL_DIR` 换成本 skill 的实际路径。民谣类慢歌可加 `--min-rate 0.6`；短歌可加 `--min-total` 调低字数下限。脚本报"必改"的，当场改，改完重新跑。输出末尾的「读音风险」清单要原样转给用户，生成后重点听那几句。

### 6. 自检

脚本只管能计算的部分。下面这些要你自己对着 `references/polish.md` 的「诊断问题」过一遍：

- 事实有没有写错
- 写真人时，按 `references/rules.md` 第七节逐句过一遍：单一来源有没有混入、事实/画面/写意的配比是否落在区间内（画面句是否多于事实句）、想象有没有越界到替对方写心理
- 有没有解释情绪的句子
- 有没有抽象词
- 副歌三次是不是在推进，而不是换说法重复
- 歌名和词的关系：点题但不点破

### 7. 输出与打磨

给用户看三样：歌词（与 `歌词定稿.md` 一致）、创作注解（韵脚方案、技法、哪些地方是想象不是事实）、校验结果摘要。然后问一句：**有没有哪一句不像你会说的话？**

用户给出反馈后，读 `references/iteration.md` 处理。逐轮：

1. 用「诊断问题」检查，并主动指出可能有问题的句子。
2. 用户指出的问题照改，只改指出的，并说明哪些没动。
3. **每轮改完立刻写入 `歌词定稿.md`，重跑校验脚本。**

用户说"满意"才进入下一步。只要词，不要出歌，到这里就可以结束。

### 8. 选平台，生成提示词

**先问两件事**：用哪个软件（二选一，也可以两个都要），以及想要**男声还是女声**（不要根据歌里人物的姓名、称呼去推断性别，让用户选）。

| 平台 | 读哪个文件 |
|---|---|
| Suno | `references/suno.md` |
| 海绵音乐 | `references/haimian.md` |

曲风让用户**听着选**：给 3 档预设（见各平台文件），每档用一句人话描述，而不是术语。输出完写入 `提示词-Suno.md` / `提示词-海绵音乐.md`。

### 9. 生成后检查

用户出歌后，读 `references/check.md`，带用户听三处、只局部重做。校验脚本输出的「读音风险」清单一并给用户。

### 10. 交付

最后给用户一页纸：歌词定稿、提示词、发布提醒（见 `references/polish.md` 的「红线」）。

## 底线

- 不涉黄、暴力、违法、政治敏感、仇恨言论。
- 不把想象说成事实，尤其是写真人。
- 不用真实歌曲名做歌名；不在歌词里原样引用他人歌词；不在提示词里写真实歌手名字。
- 写真实人物和未了结的事：标"粉丝二创"或"虚构创作"，不替当事人下结论。
- 不要一次生成后发现问题就整首重跑，先定位，只重做出问题的那一段。
- 不要承诺"一定能出爆款"。能做到的是：**一两个小时，从一个故事到一首能听的歌。**
